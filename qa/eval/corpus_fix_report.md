# 知识语料修复效果报告（结构化知识 → 向量库）

> 实验日期：2026-09-24
> 目的：验证「把 `data/new_energy.json` 渲染成语料并单独入库」是否真正解决
> "检索消融无法可信归因"的问题。

---

## 一、问题背景

Week2 的检索消融跑在**原始 PDF 语料**（`newenergy_docs`，1094 chunk）上时，
发现两个反常现象：

1. 检索排名第一的常是**不相关文档**（问储能电池，首条是光伏路线图目录页）；
2. **混合(RRF) 反而低于纯 BM25** —— 与 RRF 融合的预期相悖。

根因定位（实测）：

| 证据 | 数值 |
|---|---|
| 语料语言构成 | 英文 chunk **928** vs 中文 chunk **139**（87% 英文） |
| 单一来源占比 | `GlobalEVOutlook2025.pdf` 独占 **925/1094** chunk |
| chunk 缺少 `section` | **1078/1094**（98%），PDF 标题未解析 |
| **评测期望实体覆盖率** | **20/56 = 36%** |

即：超半数评测题目的期望实体在语料中**一次都没出现**，文档检索组注定零召回。
指标反映的是"语料缺失"，而非"检索策略优劣"——实验失去归因能力。

---

## 二、修复方案

不改既有摄取管道，新增一层**渲染层**（`qa/ingestion/kb_renderer.py`）：

```
data/new_energy.json (63 条技术记录，单一事实来源)
    ├──► graph/build_newenergy_graph.py ──► Neo4j          （已有，未改动）
    └──► kb_renderer ──► docs/kb/<类别>/<技术名>.md (63 个)
                            └──► qa.ingestion.run ──► Qdrant 集合 newenergy_kb
```

关键设计：

- **一条技术 = 一个文件**：`compute_doc_id()` 按文件内容算 SHA-256，
  因此新增技术只需加一个文件即可被增量识别，无需重建集合；
- **文件内用 `##` 分 5 个字段组**：`chunker` 自动生成 section 路径，
  治好了 PDF 那 98% 缺 section 的问题；
- **空值不渲染**：避免无信息量的 chunk 稀释检索。

**渲染层覆盖率自检结果：56/56 = 100%**（对比原语料的 36%）。

摄取结果：63 个 md 文件 → **378 个 chunk**（平均 6 chunk/文件，1190 字符/文件）。

---

## 三、消融对比（同一评测集、同一 K=5、同一判定口径）

判定口径：`qa/eval/dataset.py::judge_result`，期望实体出现在检索文本或章节路径中即视为相关。

| 检索配置 | Recall@5 | MRR | Precision@5 |
|---|---|---|---|
| 纯KG图谱 | 67.0% → **67.0%** | 0.6700 → **0.6700** | 29.6% → **29.6%** |
| 纯向量 | 28.0% → **91.0%** | 0.1968 → **0.8253** | 7.4% → **50.2%** |
| 纯BM25 | 39.0% → **90.0%** | 0.2943 → **0.8355** | 12.0% → **65.4%** |
| 混合(RRF) | 35.0% → **90.0%** | 0.2508 → **0.8375** | 9.4% → **61.4%** |
| 混合(RRF)+重排 | 32.0% → **90.0%** | 0.2500 → **0.8598** | 10.0% → **62.8%** |

（每格为 `修复前(PDF语料) → 修复后(结构化知识语料)`；KG 组不依赖文档语料，故不变。
原始报告：`ablation_before_pdf.md` / `ablation_after_kb.md`）

### 关键结论

1. **文档检索三指标全面跃升**：纯向量 Recall@5 从 28% → 91%，
   Precision@5 从 7.4% → 50.2%（约 6.8 倍）。
2. **"混合不如单路"的反常消失**：
   - 修复前：混合 RRF(35%) **低于** 纯 BM25(39%) —— 融合在污染语料上起了反作用；
   - 修复后：混合 RRF(90%) 与纯 BM25(90%) 持平，但 **MRR 更高**（0.8375 vs 0.8355）。
3. **重排第一次体现增量价值**：MRR 0.8375 → **0.8598**（+0.0223）。
   修复前重排是**负收益**（0.2508 → 0.2500）。
4. KG 组纹丝不动（67%），**佐证变量控制干净**：本次只换了文档语料，图谱路径未被触碰。

## 四、必须说明的局限（诚实清单）

1. **存在同源自洽性问题**：`docs/kb` 的语料源自 `data/new_energy.json`，
   而评测集的期望实体也大量来自同一批技术。因此"语料覆盖期望实体"这件事
   本身带有同源性质，91% 这个数字**不能直接等同于"在真实语料上的检索能力"**。
   它是"语料覆盖率"的有效度量，但不是独立泛化能力的证明。
2. **修复的是语料，不是算法**：本报告证明的是"语料决定检索上限"，
   而非"RRF/重排算法更优"。算法优劣需要在**独立语料**上验证。
3. **BM25 与向量高度接近**（90% vs 91%）：在短小、术语密集、答案即实体名的
   结构化语料上，词面匹配已接近饱和，语义检索的优势区间被压缩。
4. **判定为 LLM-free 近似**：关键词/实体命中不等于语义相关性，仍可能高估。

### 下一步建议（若要让结论更硬）

- 换用**与出题无关的中文语料**（如行业报告）做留出集，重跑消融，去掉同源偏差；
- 用**改写问句**（不与语料同词）复测，检验语义检索的真实增益；
- 把英文 PDF 单独成集，量化跨语言检索损失（**受阻**，见下节）。

## 四之二、补充测量：根因是"词汇缺失"，不是"语言不同"

后续补充调查**修正了本报告早期的表述**。此前把问题主要归因于
"语料 87% 是英文、中文查询与英文语料跨语言不匹配"。实测后应更精确地说：

| 口径 | PDF 语料 `newenergy_docs` | 知识语料 `newenergy_kb` |
|---|---|---|
| 领域实体名（63 个技术名）覆盖 | **20/63 = 31.7%** | 59/63 = 93.7% |
| 评测期望实体（56 个）覆盖 | **20/56 = 35.7%** | **53/56 = 94.6%** |
| chunk 语言构成 | 英文 84.8% / 中文 12.7% / 混合 2.5% | 中文为主 |

PDF 语料中**完全缺失的期望实体共 36 个**，例如 磷酸铁锂电池、三元锂电池、
华龙一号、AP1000、碱性电解水制氢、半片组件、V2G技术 等。

**结论修正**：英文占比高是**相关现象，但不是主因**。即使按语言把语料拆开，
只要语料里根本没有这些领域词汇，检索同样为零——这是"知识边界未覆盖"，
而非"跨语言匹配能力不足"。因此"英文 PDF 单独成集"的价值主要是
**量化跨语言检索损失**，而不是解释本次消融的差距。

**一个被推翻的中间假设（记录以免重蹈）**：实测 BM25 对 100 道中文查询的
"词可匹配率"达 78.1%，仅 2 道题一个词都匹配不上。乍看像是"BM25 没问题"，
但该口径把「电池」「材料」这类**泛词**也算作命中，掩盖了「磷酸铁锂」这类
**特征词缺失**——泛词命中没有区分度，检索排名因此被无关文档占据。
**教训：衡量语料覆盖要用领域特征词，不能用全体词。**

### 仍未完成的测量（受阻原因）

- **跨语言检索损失的精确量化**：需要向量检索与重排 API，当前 DashScope
  账号欠费（`400 Access denied ... overdue-payment`），**受阻**。
  仅用 BM25 无法给出有意义的跨语言对比（中文查询对英文文本的词法命中率为 0）。
- **重排候选池 `cand=30` 的第二语料验证**：同样依赖 rerank API，**受阻**。
  已有线索：PDF 语料上重排曾是**负收益**（MRR 0.2508 → 0.2500），
  而知识语料上是正收益（0.8375 → 0.8665），说明重排效果强依赖语料质量。

## 五、复现命令

```bash
# ① 覆盖率自检（离线，不烧 API）
python -m qa.ingestion.kb_renderer check

# ② 渲染（幂等：内容未变则报告"新写 0"）
python -m qa.ingestion.kb_renderer render

# ③ 摄取进独立集合
python -m qa.ingestion.kb_renderer render --ingest --collection newenergy_kb

# ④ 消融（修复前 / 修复后）
python -m qa.eval.run --output qa/eval/ablation_before_pdf.md
python -m qa.eval.run --collection newenergy_kb --output qa/eval/ablation_after_kb.md
```
